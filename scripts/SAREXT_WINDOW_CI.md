# Selected SAR/SAREXT output-window evidence

This isolated controller evaluates the reviewed upstream four-file generator change, before deciding whether to publish a draft PR. It does not modify the consumer implementation or measure Polars `.over()`. The immutable candidate is deliberately unset until independent controller review and a separate two-line activation.

Each of two Ubuntu jobs compares C TA-Lib 0.8.3 (`62021c1d14ef5499505af5547384cab509adf3fc`), current upstream Rust (`ccd3172940ed1d9daa4e7197f2265810852e8910`) and the candidate on the same runner. Rust 1.90.0 and 1.97.0 are separate experiments; no ratios or distributions are pooled across jobs. The library declares MSRV 1.88. The root development-toolchain pin of 1.97 is not an MSRV declaration, and this workflow does not establish 1.88 performance.

All arms use fresh source builds. Rust uses portable release O3, ThinLTO, one codegen unit, no native target flags or force-dispatch hooks. The normal public typed API chooses its ordinary hardware path. C is built in release mode from the official tag. Artifact records retain exact commands, environment, compiler versions, CPU description, sources, archives, rlibs/fingerprints, executable hashes and actual executable disassembly. These provenance records bind builds but do not claim a unique instruction-by-instruction rlib-to-ELF proof.

## Gates before timers

The 1.97 source job runs generator tests, strict generator/library Clippy, library tests/doctests, full regeneration and all 237 generated C and Rust indicator regressions. Successful source logs and exact frozen candidate hashes are verified by each measurement job. Each toolchain additionally runs both exact Rust libraries' release tests. The code-generation inspector analyzes the actual ordinary benchmark executables before the test builds can change Cargo caches.

The bounded ELF64 x86-64 inspector reads GNU `readelf` symbol bounds/segments/relocations and GNU `objdump` instructions with raw bytes. Every scoped function must decode contiguously through its exact symbol size; missing bytes, overlapping bounds and unresolved instructions fail closed. Its iterative SCC analysis records all cyclic regions, backedges, non-stack f64 stores, floating arithmetic, reachable panic branches and unknown calls/exits. Under the frozen source invariant of one mutable f64 output and no local f64 arrays, a store/arithmetic cycle is an output-loop candidate. For the 1.97 candidate, each SAR/SAREXT generic/FMA function family must have exactly one output-loop candidate with no reachable bounds panic or unknown call/exit. Unknown scope fails before timings. All fallback loops remain in the report. Version 1.90 records its actual checks/unknowns/code growth without pretending the check-free mechanism is established there.

SCC analysis alone does not establish register-value provenance or which path a runtime call selects. The separate frozen source proof supplies valid-prefix and dispatch preconditions. Actual CPU observations and the public-call capture checks supplement that proof; a scalar function's disassembly is not a measured scalar speed result.

All 45 arm/case captures complete before the first measurement child. They contain each selected full output plus 180 records: ten ranges across the fixture prefix and 17 distinct IEEE input patterns. Records preserve beginning/count, full physical buffers and NaN-payload canaries. The C driver never passes short buffers to a length-unaware C API; separate native probes exercise two short consumed inputs and a short output. All arms check three invalid ranges and applicable nonfinite options. Native baseline/candidate captures must match every bit. C/native non-NaN bits, signed zero, infinities, range metadata and all unwritten tails match exactly. Written NaN positions must match; every sign/payload difference is retained explicitly. No finite numerical tolerance or signed-zero waiver applies to this focused harness.

## Workload and reporting

Fifteen typed cases cover SAR and SAREXT, each with default and reversal-heavy parameters, at 100, 10,000 and 1,000,000 rows. Three matching ADD sizes are unchanged controls. Six physical input snapshots are retained. Reversal coverage must include both SAREXT signs or SAR prices on both sides of the input range. Results include both function families and every control; no losing case is removed.

Each job pins the controller and its children to one available CPU. Every case alternates all six three-arm orders twice (12 rounds), giving each arm four appearances in each order position. A fresh selected child performs five warmups and 31 inner samples. Fixed iterations per sample are 1,000/10/1 at the three lengths. Thus each job contains 540 children and 16,740 samples; the two jobs together contain 1,080 children/33,480 samples, without pooling their comparisons. Every timed child rechecks its selected full output against a retained C-derived golden before and after timing. Duplicate selected captures are deleted only after their hashes and sizes are recorded; complete preflight captures and goldens remain in the artifact.

The controller has a 600-second measurement budget and 30-second child timeout; workflow jobs allow 120 minutes for builds/gates. Failures retain logs and completed-child ledgers. Repetitions are not truncated to obtain a result. Reports retain all process medians, all three pairwise comparisons, paired ratios, round wins, descriptive envelopes and every slower median. Paired ratios and envelopes use before/after latency, so values above 1 favor the later arm; the signed latency percentage uses after/before minus 1. Envelope separation is descriptive, not a confidence interval; inner samples correlate and shared-runner interference remains. Driver dispatch and range assertions are included. Whole-child fault counts also include startup, fixture/golden I/O and warmups, so they cannot isolate allocation cost.

No local timing constitutes performance evidence. CI results determine retention/publication, including regressions on the older compiler. No merge or release is performed by this workflow.
